How fourway checks a pair

Git's merge is three-way: it compares text on the base and both sides. Fourway adds the fourth tree, the merged result, and compares behavior.

  1. Read both changes

    The diffs, the code they touch, and what each author said the change is for.

  2. Write tests

    Aimed at how the two changes interact, not at either one alone.

  3. Run four trees

    Each test runs on the base, A, B, and the merge, more than once.

  4. Read the pattern

    The four outcomes show whether the merge lost what a change needed.

  5. Return a repro

    A conflict comes back as a failing test for the change to revise.

  6. Keep the evidence

    Tied to exact commits and tests, and expires when any of them change.

def test_lost_response_never_captures_twice():
    gateway = FakeGateway(faults={1: "timeout_after"})
    try:
        charge(ORDER, gateway)
    except GatewayTimeout:
        pass
    captured = gateway.captured("ord_1")
    assert len(captured) == 1
    assert sum(c.amount_cents for c in captured) == 1250

Claude wrote this test from the two diffs and their descriptions. It passes on the base, on A, and on B, and fails only on the merge, so either agent can run it to reproduce the bug.

The first three findings are conflicts. A test whose outcome changes between runs is flaky and excluded, and a pair with no usable test is unverified, never clean.

From a check to the merge layer

Git keeps your code. Fourway adds the layers Git doesn't have: what each change is for, which changes can collide, and proof that what landed together works together.

CI made “it builds” a fact for every change. Fourway makes “it works together” a fact for every merge.

  1. Agent APIPlannedAgents ask what's in flight near their code and whether a combination was verified.
  2. Evidence ledgerBuiltWhich exact commits, environment, and tests were verified, and when that expires.
  3. Kept testsPlannedEvery catch stays as a permanent check with no model cost.
  4. Four-way verifierBuiltGenerated tests on the base, each change, and the merge.
  5. Interaction graphPlannedFinds the pairs that share code or rules.
  6. Change recordsPlannedWhat each change is for, what it relies on, and its side effects.
  7. GitYours todayStores the code. Nothing about how you branch or merge changes.

In every pull request

  • Merge checkPlanned

    A status check on each pull request: verified against the changes in flight, or the failing test that shows why not.

  • Revise loopPlanned

    The failing test goes to the agent whose change should revise. It fixes forward, and fourway checks the pair again.

  • Merge certificatePlanned

    Every merge records what it was verified against, so “was this tested with that?” has an answer later.

Across the repository

  • History backtestNext

    Point fourway at recent merges and see which pairs it would have flagged, before you change any workflow.

  • Rules filePlanned

    Write the behaviors that must always hold, such as a customer is charged at most once per order, in a file in the repository. Every pair is checked against them.

  • Deploy gatePlanned

    For teams without a merge queue, fourway checks each batch that landed together before it deploys.

For your agents

  • Conflict forecastPlanned

    Before an agent edits, it asks over MCP what else is in flight near that code and which rules apply, and steers around the collision.

  • Verified lookupPlanned

    Any agent or CI job can ask whether a set of commits was verified together and get the evidence back.

  • Learns from incidentsExploring

    Connects flagged conflicts to the incidents that followed, so the pairs it checks first improve with every deploy.

Beyond application code

  • Feature flagsExploring

    Two flags are two changes that stay in flight. Both off, A on, B on, and both on is the same four-way grid.

  • Prompts and agent configsExploring

    One person edits a system prompt while another edits a tool schema. Your evals become the tests.

  • Infrastructure and migrationsExploring

    Plans and policy checks on four trees before anything applies, and migrations checked against readers still on the old schema.

Measured in the open, including what it can't prove yet

Fourway is a benchmark today, not a tool for your pull requests. It has to clear three bars first, and every scored run is committed with its generated tests and outcomes.

  • Conflicts found 6 of 6seeded conflicts
    Bar: 50% or more 0%100%
    Above the bar

    The 95% interval, 61% to 100%, is above the bar. Claude wrote both the cases and the tests, so they might share blind spots, and the three conflicts in real repositories follow one shape. Six cases can't separate 61% recall from 100%.

  • False alarms 1 of 6clean pairs
    Bar: under 5% 0%100%
    Not proven yet

    The flagged pair has a real bug in one change alone. A test that also used the other change's new code made it read as a conflict, and the benchmark's rules count that against the generator. Proving under 5% takes at least 73 clean pairs with none flagged.

  • Model cost $0.24per pair
    Bar: under $5 $0$6
    Clears the bar

    $2.82 in total for twelve pairs, with one model call per pair. Pairs in real repositories averaged $0.39, and none cost more than $0.50.

Run 3, Claude Opus 5.5, 2026-10-30, on twelve cases: six conflicts and six clean pairs, half of each seeded into real open-source repositories. Corpus v4 adds 24 clean pairs mined from real pull requests, and no generator has run on v4 yet. Published test-generation research found about a third of semantic conflicts (SAM detected 9 of 29).
